# 회부: 수집 빈도와 저장소 부담의 균형

## 무엇을 만들고 있나
perp 거래소 10곳의 **호가창 슬리피지**를 주기적으로 재서 공개 리포트를 만든다.
공개 API 만 쓰고 주문은 하지 않는다. 목적은 "GRVT 가 유동성 경쟁에서 어디쯤인가"에
정직하게 답하는 것. 최근 추가한 핵심 지표가 **스파이크(튐)** 다 —
"평균은 좋은데 가끔 크게 당한다"를 중위값이 숨기기 때문.

## 지금 구조
```
오사카 Oracle Free 서버 (2 vCPU / 1GB RAM / 45GB, 상시 가동)
  cron 5분마다  → 한 라운드 수집 (거래소 10 × 종목 20 × 규모 5 × 매수/매도 = 2,200행)
  매시 00~09분  → 집계(agg) → 리포트(HTML) → git push
                                    ↓
                            GitHub Actions → Cloudflare Pages 배포
```

## 실측한 사실
- 한 라운드 소요: `pace 2.0초 → 57초`, `1.0 → 39초`, `0.5 → 20초`, `0.0 → 20초`
  (0.5 아래로는 안 빨라진다. 네트워크가 병목. 전 구간 api_fail 0, 단발 측정)
- 서버 부하: load average 0.00, 메모리 956MB 중 339MB
- 저장소: 현재 19.1MB / 커밋 46개 / **커밋당 0.42MB**
- 커밋에 담기는 것: agg_latest.json 0.34MB + rank_history.json 0.19MB + index.html 0.50MB
- 원시(csv.gz)는 방금 .gitignore 에 넣어 **git 에서 뺐다** (24시간만 쓰고 지우는데
  git 은 히스토리에 영구히 남기 때문)
- GitHub 한도: 권장 1GB / 실질 5GB. 지금 속도로 1GB 까지 매시간 커밋 기준 **약 3.4개월**

## 풀어야 할 것
수집을 **1분 간격**으로 당기고 싶다(스파이크를 5배 조밀하게 잡으려고).
수집 빈도 자체는 git 부담과 무관하다(집계는 여전히 매시간 1회).
진짜 부담은 **매시간 커밋 0.42MB** 이고, 3.4개월이면 1GB 에 닿는다.

## 내가 떠올린 선택지
- A) 리포트(index.html 0.5MB)를 git 에서 빼고 서버가 Cloudflare 로 직접 배포 → 7개월
- B) 집계·커밋을 4시간마다 → 13개월. 단 리포트도 4시간마다만 갱신
- C) 그대로 두고 3개월 뒤 히스토리 정리
- D) 수집만 1분으로 하고 나머지는 유지

   아니면 표본이 늘 뿐 같은 것을 더 자주 보는 것에 불과한가?

   그리고 절대 bps 병기)에 방법론적 함정이 있나?
   ★이미 하나 알고 있다: 기준선이 0.006bps 처럼 작으면 2.5bps 만 나와도 398배가 된다.
