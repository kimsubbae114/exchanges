아래는 냉정한 결론이다.

1) 구조/선택지 평가
- B, D: 목적과 어긋남. B는 신선도 희생(스파이크 놓침), D는 저장소 부담 해결 안 함.
- C: 3개월마다 히스토리 재작성은 투명성·재현성에 안 좋고 운영 리스크 큼. 권하지 않음.
- A: index.html만 빼봐야 3.4→7개월에 불과. 근본 해결 아님.
- 권고(E): “GitHub에서 데이터 떼어내기”
  - GitHub는 코드만. 데이터(시간축 히스토리)는 오브젝트 스토리지(R2/S3/B2)나 Cloudflare KV/D1에 일/day 단위 NDJSON.gz(or Parquet+zstd)로 보관.
  - 리포트는 Cloudflare Pages Direct Upload API로 배포(깃 의존 제거). HTML은 가볍게 두고, 필요한 시계열은 클라이언트가 R2에서 fetch.
  - 집계 주기는 시간당 1회 유지 가능(페이지는 시간당 1회 빌드), 수집 주기는 1분으로 올려도 Git 영향 0.
  - 장점: 용량 압박 해소, 델타 압축 걱정 불필요, 신선도 유지.
- 대안(F): GitHub Releases/Artifacts에 일별 압축 파일 업로드(리포지토리 히스토리에 안 쌓임). 페이지는 Releases URL에서 로드. 운영 단순함이 장점.

2) 1분 간격의 통계적 의미
- 의미 있다. 주기 T로 스냅샷할 때, 지속시간 d(초)인 스파이크를 “한 번이라도 맞출” 확률은 대략 d/T. 5분→1분은 탐지확률 5배 증가.
- 다만 스파이크가 수초급이면 1분도 여전히 거칠다. 가능하면:
  - 웹소켓(탑오브북)으로 감시하다 스프레드 급확대/미드 점프 시, 해당 거래소·심볼 “즉시 풀북 REST 수집” 트리거(사건기반 오버샘플링).
  - 크론은 1분 정시 고정 대신 ±몇 초 지터 부여(위상 고정에 따른 에일리어싱 방지).
- 20초/라운드라면 1분 주기는 여유롭다. 레이트리밋만 주의.

3) 스파이크 지표의 함정과 수정
- 매우 작은 기준선(중위값) 대비 배수 폭주: 이미 인지. 해결책:
  - 절대값(bps) 기반 임계(예: >2/5/10 bps)와 배수 기준을 병행. 배수 계산은 log(slippage_bps + c)에서 수행(c는 0.5~1 bps 같은 바닥값).
  - 또는 기준선을 “시간대별(시간-요일) 롤링 Q50”로 하고, 바닥값 ε(bps) 적용.
- p99 안정성: 1시간 창에 60개면 p99 추정은 거의 무의미(표본 기대치 <1). 최소 수천 샘플 창(≥1주) 또는 POT(EVT, GPD)로 tail 모델링. 신뢰구간(부트스트랩) 제시 권장.
- 최대값(max multiple): 극도로 불안정. 보고하되 핵심 평가는 ES(Conditional tail mean, 예: ES95)와 exceedance rate로.
- 동시성/공정성: 10거래소를 ~20초에 순차 수집하면 시점이 다름. 라운드마다 랜덤 셔플 또는 가능한 동시 수집으로 편향 완화. 각 포인트에 타임스탬프와 “북 스테일(age)/깊이 컷오프” 메타데이터 기록.
- 데이터 품질: API 결측/유지보수/깊이제한으로 슬리피지 급등처럼 보이는 경우가 있음. QC 룰 추가(예: 스프레드가 X bps 초과·호가수준 N 미만·북 age>Y ms 시 별도 플래그/제외).
- 표본 가중: 시간가중은 “임의 도착 테이커”에 적합. 필요 시 거래량 가중 보조지표 병기.
- 보고: buy/sell 분리 유지, 사이즈별 지표는 로그스케일 시각화 추천.

4) 저장소 부담 줄이는 방법
- 데이터 분리(최선): 일별 NDJSON.gz(+ 인덱스 manifest.json). 리포트는 외부 스토리지에서 불러옴.
- Git 안에 남겨야 한다면(비추천):
  - rank_history를 일별 파일로 분할해 변경 범위 축소, key 정렬 고정·미니파이로 델타 효율↑.
  - index.html은 최소화하고 데이터는 외부 JSON에서 로드. HTML에 base64/대용량 인라인 금지.
  - 정기 git filter-repo로 히스토리 슬리밍은 최후수단(해시 변경·fork/clone 혼란).
- 전송/서빙 최적화: 서버 사이드에서 brotli/gzip, 클라이언트 캐시/ETag. Git 용량엔 영향 없지만 트래픽 절감.
- 저비용 아카이브: Cloudflare R2/B2에 30/90일 라이프사이클 정책, 장기 아카이브 전환.

요약 권고안
- 수집: 1분 + 지터, 가능하면 웹소켓 트리거식 오버샘플링.
- 지표: 절대 bps 임계 + 로그배수, ES95, POT/부트스트랩, 최대값은 보조. 시간대별 기준선·ε 바닥.
- 공정성: 수집 순서 셔플/동시화, 메타데이터(QC) 기록.
- 배포/저장: 코드만 GitHub. 데이터는 R2/Releases. Pages Direct Upload로 HTML 배포. 리포트는 시간당 1회 집계로 유지.

이렇게 하면 스파이크 관측력(빈도↑)과 공개 리포트(신선도 유지)를 해치지 않으면서 저장소 문제를 근본 해결한다.
